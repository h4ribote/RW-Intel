# 方策の評価

二つの方策のどちらが強いかを判定する手順である。**採点、必要エピソード数、エピソードごとの記録、方策の差し替えによる比較のすべてが実装済みである。** 実物は `rwintel/eval` にあり、`python -m rwintel.eval` で動く。ここに書くのは方式の決定と、それを支える実測である。

評価を早く決める理由は [01-architecture.md](01-architecture.md) にある。同一の乱数種と設定を与えても試合は再現しないため([../game/05-match-control.md](../game/05-match-control.md))、片方の方策を差し替えて同じ展開で比べることができない。**評価は最初から多数エピソードの平均として設計する必要があり、以降のすべての判断がこれに依存する。**

## 実測: 内蔵 AI 同士は決着しない

評価の設計を始める前に、対戦がどう終わるのかを測った。

| 項目 | 値 |
| --- | --- |
| マップ | Islands (4p) |
| 対戦者 | 内蔵 AI 2 名、他は観戦 |
| 難易度 | 両者とも Hard |
| 開始クレジット / 開始ユニット / 収入倍率 | 4000 / 建設機 1 体 / 1.0 |
| 霧 | 視線 |
| 打ち切り | ゲーム内 25 分 |
| 実行 | 8 並列、速度倍率 10 |

**結果は、集めたエピソードのすべてが打ち切りであった。** 生存チームは最後まで 2 つのままで、勝者が決まらない。

| 項目 | 値 |
| --- | --- |
| エピソード数 | 45 |
| 決着 | 0 |
| 打ち切り | 45 |
| 打ち切り時のユニット数 | 平均 111、標準偏差 11、範囲 87 から 134 |

同じ難易度の内蔵 AI 同士は、25 分では互いを崩せない。序盤に取った資源地点を守り合い、前線が動かなくなる。

**この 45 エピソードは計算し直せない。** 内蔵 AI どうしの測定は `local/episodes/` のエピソード記録ではなく `tools/windows/Measure-MatchOutcomes.ps1` が残す実行ログから読むもので、そのログは後の実行に上書きされている。**測定であることは変わらないが、再現できるものとして読んではならない。** ログが残っているのは下の[難易度に差を付けた 24 エピソード](#実測-難易度に差を付けても決着しない)の方であり、そちらは全項目が読み直せる。**二つは別の集合である。** 上のユニット数と下のそれは一致しない。

## 帰結: 勝敗だけを主指標にはできない

勝率は二値であり、その標準誤差は `sqrt(p(1-p)/n)` である。勝率 0.5 のあたりで差 δ を有意水準 5 パーセント・検出力 80 パーセントで検出するには、片側あたり `7.85 × 2 × 0.25 / δ²` エピソードが要る。

| 検出したい勝率差 | 片側あたりのエピソード数 |
| --- | --- |
| 0.05 | 1570 |
| 0.10 | 393 |
| 0.15 | 175 |
| 0.20 | 99 |
| 0.30 | 44 |

数字そのものは扱える大きさに見える。**問題は、この観測がそもそも得られないことである。** 実測した 69 エピソードのうち、決着したものは 0 であった。勝率を推定する材料が一つもない。

したがって**主指標は打ち切り時の盤面を採点する連続量とする。** 勝敗は、それが付いたときに採点を飽和させる形で組み込む。

## 採点

エピソードの終わりに、自軍から見た優劣を `-1` から `+1` の範囲で採る。

```
決着したなら  score = +1(勝ち) または -1(負け)
打ち切りなら  score = clamp(w_m * m + w_e * e + w_t * t, -1, +1)
```

| 記号 | 量 | 定義 | 出所 |
| --- | --- | --- | --- |
| `m` | 軍事価値差 | (自軍の現有価値 - 敵の現有価値) / 両者の合計 | 価格の総和([03-script-policy.md](03-script-policy.md)) |
| `e` | 経済差 | (自軍の収入 - 敵の収入) / 両者の合計 | `n.v()` |
| `t` | 累積戦績差 | (撃破数 - 喪失数) / 両者の合計。ユニットと建物の数であって価格ではない | `l.bY.a(player)` の `c` `d` `f` `g` |

いずれも比であり、試合の長さやマップの大きさで尺度が変わらない。**素材はすべて集計値から O(1) で取れる**ので、採点自体は費用にならない([../game/03-observation.md](../game/03-observation.md))。エピソード終了時に、陣営ごとの現有価値・収入・撃破数・喪失数がゲーム側から届く。

### 累積戦績差は 1 対 1 では常に 0 になる

実装して判明した。**二陣営の対戦では、自軍の撃破数は相手の喪失数そのもの**である。したがって `撃破 - 喪失` は両陣営で符号だけが逆の同じ値になり、その差を和で割る式は分母が 0 になる。`t` は 1 対 1 では情報を持たない。

これは数え方を価値に変えても直らない。同じ打ち消しが起きるためである。`t` が意味を持つのは第三者が試合にいる場合だけであり、**1 対 1 の評価では実質 `w_t` は不定**である。重みを合わせる際にこの項を残すかどうかは、三人以上の対戦を評価対象に含めるかどうかの判断になる。

### 重みの決め方

`w_m`、`w_e`、`w_t` は未決である。**机上で決めず、決着したエピソードを使って合わせる。** 条件は「決着したエピソードで、打ち切り直前の採点の符号が実際の勝者と一致すること」である。

**そのための決着したエピソードが、いまはまだ手に入らない。** 内蔵 AI 同士は難易度に差を付けても決着せず([実測: 難易度に差を付けても決着しない](#実測-難易度に差を付けても決着しない))、決着する対戦を作るにはスクリプト方策の集団が要る。**重みを決めるのは、方策が書けてからである。** それまでは主成分の `w_m` を 1、残りを 0 とし、軍事価値差だけで評価する。

この手順を採るのは、採点が勝敗の**予測**であってほしいからである。勝敗が付かない試合で「もし続けたらどちらが勝つか」を測るのが目的であり、そのための重みは実際の勝敗から学ぶのが筋である。

**終局の一定時間前の盤面も記録している。** 条件は「打ち切り**直前**の採点の符号が勝者と一致すること」だが、決着したエピソードの終局時には敗者は既に消えている。その盤面で重みを合わせると、実際に採点を使う場面(まだ両者が立っている盤面)より易しい問題に合わせることになり、**どの重みでも正解する問題に合わせることになる。** 計測エージェントは 5 秒ごとに陣営ごとの現有価値・収入・撃破喪失を控え、終局の 30 秒前にあたる一枚を `before`(と `before_seconds`)として finished の報告に載せる。**重みの当てはめはその盤面を使い、持っていないエピソードだけ終局の盤面に落ちる。** どちらで当てはめたかは報告が枚数で言う——終局の盤面で当てはめた分は弱い証拠だからである。

### 実測: 軍事価値差の標準偏差

採点の主成分である軍事価値差 `m` は、いま測れる。打ち切り時に生存している完成ユニットの価格を陣営ごとに合計し、差を合計で割った値である。

対称な対戦(下記)で 24 エピソードを取った結果である。

| 項目 | 値 |
| --- | --- |
| 平均 | -0.011 |
| 標準偏差 | 0.228 |

**平均がほぼ 0 であることが、この指標が対称な対戦で偏らないことを示している。** 陣営の入れ替えや地形の偏りが混じっていれば、ここに出る。

### 連続量に必要なエピソード数

標準偏差を σ、検出したい差を δ とすると、片側あたり `7.85 × 2σ² / δ²` エピソードである。実測の σ = 0.228 を入れると次のようになる。

| 検出したい軍事価値差 | 片側あたりのエピソード数 | 両側の実時間(8 並列、倍率 10、打ち切り 15 分) |
| --- | --- | --- |
| 0.05 | 328 | 2.4 時間 |
| 0.10 | 82 | 0.6 時間 |
| 0.20 | 21 | 0.15 時間 |

この表は丸める前の標準偏差から計算している。表示している 0.228 をそのまま入れると 0.05 の行は 327 になる。0.10 と 0.20 の行は丸めても変わらない。

**これが評価を連続量で行うことの利益である。** 勝率で同じ土俵に立とうとすると、そもそも決着しないので観測が得られない。軍事価値差は毎エピソード必ず得られ、10 パーセントの差なら 40 分弱で判定できる。

採点全体の σ は `w_e` と `w_t` を決めてから測り直す。**上の値は主成分だけの下限として読む。**

### 二つ目の場合: 交戦の成績

同じ算術が、[04-learning.md](04-learning.md) の交戦アリーナにも当たる。**単位が試合ではなく交戦 1 件で、量は軍事価値差ではなく交戦の成績である。** 成績は相手が失った価値の割合から自分が失った割合を引いたもので、反対称であるから両側を同じ層にした基準線の平均は 0 でなければならない。散らばりも実測してある。両側手書き層・240 秒エピソードの基準線で 0.480(交戦 338 件)、交戦 1100 件規模の実行で 0.547 と 0.556 である。**計画には大きい方、0.55 を使う。**

**この成績からは戦力シェアの項を引く。** 抽選で決まるシェアは成績と 0.6 ほど相関しており、その固定倍率を引けば分散が落ち、しかもシェアは両側の層が何かを決めるより前に固定されるので最適方策も反対称性も動かない。**この項は一度入れ、自己検査に否決されて 0 に戻し、否決の原因を直したうえで測り直して戻してある**([../record/03-tactics.md](../record/03-tactics.md))。倍率は読みごとに別で、疎な読みが 3.96、体力の読みが 3.68 である。**以下に並べる散らばりは、いずれも補正を入れる前に取った値である。** 補正を当てると交戦あたりの散らばりは疎な読みで 4 割、体力の読みで 5 割近く落ちるので、下の必要数は上限として読む。**ただし補正が狭めるのは非対の平均だけで、二つのアームを対にした差は狭めない**——シェアは両アームに共通なので、差の中で相殺するからである。

| 場合 | 単位 | 実測した散らばり | 0.05 の差に要る単位数(片側) | その実時間 |
| --- | --- | --- | --- | --- |
| 試合の軍事価値差 | エピソード | 0.228 | 328 | 2.4 時間(8 並列、倍率 10、打ち切り 15 分) |
| 交戦の成績 | 交戦 | 0.55 | 1900 | 13 分(12 並列、240 秒エピソード) |

**散らばりは試合の倍あるのに、費用は 1 桁以上安い。** 240 秒のエピソードが平均 5.7 交戦を生み、そのエピソードが実時間 28 秒で終わるためで、12 並列なら毎秒 2 件以上の交戦が出る。**アリーナでは、散らばりが大きいことは予算の問題にならない。** 問題は差の側が小さいことであり、そちらは回す量では解けない。

**ただし、上の式に入れてよいのは独立に引かれた交戦だけである。** アリーナはエピソードごとに乱数種を作り直しており、それをインスタンス番号だけから作っていたので、**あるインスタンスの全エピソードが同じ交戦の列を引き直していた**([04-learning.md](04-learning.md) の [エピソードごとに交戦を引き直す](04-learning.md#エピソードごとに交戦を引き直す))。交戦 2000 件と報告していた実行が実際に引いていたのはおよそ 50 件であり、**件数で割って出していた 2 標準誤差は 30 倍から 50 倍狭かった。** 直してあり、上の費用の見積もりはそのまま生きる(引き直せば 1900 件は本当に 1900 件である)が、**それより前に取られた数字の区間は、その実行が何種類の交戦を引いたかを見てから読む。**

**さらに、同じ実行の中で比べるものは交戦ごとに対にする。** 比較のアームは同じ周回で同じアリーナ種を受け取り、同じ二つの予算・どちらが強い側か・同じ角度・同じ二つの編成を引く。差を交戦ごとに取れば、成績の散らばりの大部分を占める「どう引かれたか」が消える。実測で区間は半分になる。**アリーナの比較では、対にすることが最も安い分散削減である。**

**ただし「同じ交戦を引く」は、そう書けば成り立つものではなかった。** 交戦を置く場所は「いま盤面に立っているものから最も離れている候補」の中から引くもので、その候補の数は前の交戦で何が生き残ったか——すなわちその方策が何をしたか——に依存する。`random.choice` は候補の数によって消費する乱数の量が変わるので、**二つのアームはエピソードの途中で乱数列を分岐させ、それ以後は別々の予算・別々の戦力比・別々の編成を引いていた。** 対にする側はそれを知らずに引き算し続ける。**いまは場所を選ぶための第二の乱数列を持たせ、置き場所だけをそちらから引く**(`rwintel/learn/arena.py` の `placement`)。抽選のほかの消費はどれも盤面を見ない(予算も戦力比も角度も編成も、乱数列と種別表だけから決まる)ので、k 番目の交戦の抽選は両アームで同一になる。**対にした決闘が同じ交戦を引くという主張は、これで初めて成り立つ。**

**そして置かれる場所そのものは、いまも対にできない。** どこが生存者から離れているかは盤面についての事実であり、その盤面は方策が作ったものだからである。**対にした二つのアームに残るのは、同じ二つの戦力を同じ戦力比・同じ角度で、別の地面の上に置いたかもしれない差である。** 消せるものと消せないものの境目はここにあり、これは対にすることが盤面を消してもエンジンを消さないのと同じ種類の限界である。

**[04-learning.md](04-learning.md) が交戦について並べている必要数の表は、この表より緩い基準の値である。** あちらは「平均の 2 標準誤差の区間が 0 を含まなくなる大きさ」、すなわち `(2σ/δ)²` であり、上の `7.85 × 2σ² / δ²` の 3.9 分の 1 になる。二つは別のことを言っている。**2 標準誤差は、その実行の平均が 0 でないと言えるかどうかの下限**であって、**二つの実行の差を主張できる大きさではない。** 決闘が報告する必要数は厳しい方であり、緩い方を下回っている測定は何も言っていないと読む。

### 対にした比較は、二標本とは別の道具である

上の必要数の式はどれも二標本のものである。二つのアームを別々の標本として持ち、両方の散らばりを払い、片側あたり何本要るかを言う。**同じ抽選を二つのアームに引かせられる場では、これとは別の道具が使える。** 盤面ごと(交戦アリーナなら交戦ごと)に二つのアームの点を先に引き算し、差の列を 1 標本として読む。実装は `rwintel/eval/sampling.py` の `PairedComparison` と `pairs_for` であり、それが持つのは差の平均とその 2 標準誤差、両アーム単独の平均と散らばり、差の散らばりである。二つのアームが盤面を通じてどれだけ相関しているかは、その三つの散らばりから `rwintel/learn/ops_compare.py` の報告が出す。

**「同じ抽選を二つのアームに引かせられる」は前提ではなく、実装が満たさなければならない条件である。** 満たし損ねる形が二つあり、どちらもこの計画で実際に起きていた。一つは**抽選の一部が盤面を見ていること**で、盤面は方策が作ったものだから、二つのアームは途中から別の抽選を引く(交戦アリーナの場所の抽選がそうだった。[二つ目の場合: 交戦の成績](#二つ目の場合-交戦の成績))。もう一つは**対にする鍵の読み方**で、盤面の名前を「欄が有るか」ではなく「真か」で見ていると、名前が 0 の盤面だけが名前を持たないものとして別の規則へ落ちる(構築作戦アリーナの journal がそうだった。[道具](#道具))。**どちらも、対にした比較が黙って別のものを引き算する形で失敗する。** 報告される区間はそのぶん狭くなり、しかも失敗したことは報告のどこにも現れない。

**対にすることが要るのは、抽選が動かす量がアームどうしの差より大きいからである。** [04-learning.md](04-learning.md) の構築作戦アリーナでは、一つのアームのエピソードは 0.11 ほど散らばるのに、比べたい作戦選択の差は 0.04 ほどしかない。二標本で読めば、その散らばりを両側で払うことになる。**対にすれば、盤面はそこで消える。** ただし**対にすることが消すのは盤面だけである**——二つのアームを別々の実行として回したまま盤面ごとに対にしても、「別の時刻に、別のことをしている機材の上で回した二つの実行は、他は同じだった」という仮定は残る。それを消すのは対にすることではなく、**アームを一つの実行に入れること**である([最良として選ばれた差は、選択に使っていない実行で測り直す](#最良として選ばれた差は選択に使っていない実行で測り直す))。

**必要数は、散らばりが同じなら二標本のちょうど半分である。** 対にした比較は `7.85 × σ² / δ²` 対であり、二標本の `7.85 × 2σ² / δ²` の半分になる。理由はその係数 2 そのものである——二標本は二つの標本の分散を足すので σ² が二度入るが、対にした比較が持つ標本は差の列ひとつしかない。**ただしここでの σ は、どちらかのアームの散らばりではなく差の散らばりである。** 二つが同じでないことが、対にすることの利益であり、同時にその限界でもある。

**対にすると盤面は消えるが、戦いは消えない。** 同じ盤面を二度打っても、それは同じ構築ではあっても同じ戦いではない。エンジンは差分駆動で再現しないからである([../game/05-match-control.md](../game/05-match-control.md))。**その大きさは実測してある。** Hills・catchment 半径 400・地平 300 秒、種 60001 で共有した 65 盤面において、学習した作戦層は単独で **+0.0673(標準偏差 0.1142)**、固定配置は **+0.0588(標準偏差 0.1031)**、対にした差(学習 − 固定)は **+0.0086、2 標準誤差 0.0306** である。差の散らばりは **0.1233**、対にしなければ **0.1538** だったので、**二つのアームは盤面を通じて +0.36 相関しており、対にすることが差の散らばりの 2 割を取った。** 分散で読めば盤面は散らばりの 3 分の 1 ほどであり、残りは戦いそのものである。**すなわち対にすることが消すのは盤面であって、エンジンではない。**

**費用で言えばこうなる。** 差 0.04 をこの散らばりで分解するには、対にすれば 75 対(エピソード 150 本)、対にしなければ、その二つのアームのプールした散らばり 0.1088 で片側 117 エピソード(合計 234 本)である。**盤面が散らばりの一部でしかないこの場でも、対にすることは費用を 3 分の 1 以上落とす。** 交戦アリーナで区間が半分になるのと同じ道具であり、そちらの実測は[二つ目の場合: 交戦の成績](#二つ目の場合-交戦の成績)にある。

**散らばりが 0 に見える標本は、散らばりが無いのではなく、散らばりが測れていない。** すべての対が同じ点になった列の標本標準偏差は正確な 0 にならず、二進の丸めの残り(0.4 の差を 20 個で 6e-17 ほど)になる。それを散らばりとして必要数の式に入れると必要数は 0 に落ち、**対 1 組で比較が決着したと宣言する**ことになる。`sampling.py` は、平均の絶対値と 1 の大きい方に対する比が `1e-9` を下回る散らばりを「散らばりの測定が無い」として扱い——成績が 1 を下回るこの計画では、そのまま `1e-9` の絶対的な床である——、その比較は分解せず、必要数を無限大とする。**算術の最下位ビットの上で差を主張しないための床である。**

### 最良として選ばれた差は、選択に使っていない実行で測り直す

上の必要数の式は、**一つの差を一度測ったとき**に何本要るかを言う。いくつかの設定を回して最も良かったものを取り出したときには、何も言わない。三つ回して最良を取れば、その最良は選択の分だけ上に振れた推定であり、式はその分を知らない。

**これは机上の注意ではない。この計画は実際に二度間違えている。** 一度目は戦術層で、三つの設定のうち最も良かったものが交戦 333 件で +0.076、2 標準誤差の区間が 0 を含まなかった(**上の厳しい方の基準はその差に 638 交戦を要求するので、そちらは満たしていない**)。**同じ設定を、選択に使っていない種で回し直すと、交戦 1065 件で +0.005 になった**([../record/03-tactics.md](../record/03-tactics.md))。

**二度目は、その設定を二度延長して最も良くなった方策である。** 選択に使ってきた種の上では交戦 551 件で +0.061、やはり区間が 0 を含まなかった。**一度も使っていない種で測ると交戦 1107 件で +0.026 になり、同じ種で同時に取った両側手書き層の基準線が交戦 1141 件で +0.016 だったので、差は +0.010、区間は ±0.047 である。** 区間が 0 を含まなかったことは、二度とも、差があったことを意味しなかった。

**二度目は基準線の要否も示している。** +0.026 だけを見れば方策の数字だが、その種ではアリーナ自身が +0.016 側に出ていた。**基準線を同じ種で同時に取っていなければ、アリーナの偏りを方策の手柄として報告していた。** 決闘は既定で基準線のアームを同時に回すようにしてある([04-learning.md](04-learning.md) の [手順](04-learning.md#手順))。

したがって手順に一つ足す。**複数の候補から選んだものは、選択に使った測定とは別の実行で測り直し、その二度目だけを差として報告する。** 一度目は候補を並べるための測定であって、それ自体は主張ではない。乱数種を変えても試合は再現しない([../game/05-match-control.md](../game/05-match-control.md))ので、ここで種を変えることは「同じものをもう一度」を意味しない。**意味があるのは、選択に使った標本と確かめに使う標本が別であることだけである。**

**そのために、報告する数字にはそれを取った乱数種を併記する。** 種は再現のための情報ではなく、**その数字が候補選びに使った標本の上のものか、確かめの標本の上のものかを読者が判定するための情報である。** 種を書かない数字は、上の二つの誤りのどちら側にいるのかを言っていない。

**確かめの側では、比べるアームを一つの実行に入れる。** 種を分けることは「選択に使った標本と確かめの標本が別である」ことを保証するが、確かめの種の上で二つのアームを別々の実行として回せば、今度は「その二つの実行は、アーム以外は同じだった」という仮定が入る。それは仮定であって測定ではない。**構築作戦アリーナの `rwintel.learn.ops_run` は `--our` を繰り返すと複数のアームを一つの実行に入れ、盤面もインスタンスも機材の同じ瞬間もアームどうしに共有させる**([道具](#道具))。アームはインスタンスの中で交互に回り、盤面は全アームが打ち終わるまで進まないので、一つの実行がそのまま[対にした比較](#対にした比較は二標本とは別の道具である)になる。**別々に取った生値を引き算する読み方は、戦術層で実際に三度誤った読みを生んでいる。**

**その実装がいまの制御エージェントであり、詰まっている。上の 211 秒は計測エージェント(`tools/probe-agent`)の数字であって、評価と学習が通る経路のものではない。** 制御エージェントは終了検出を戦術周期(既定 200 ゲームミリ秒)で行い、次のエピソードをその場で始める。**実測**——構築作戦アリーナの 8 並列・倍率 10・ゲーム内 360 秒のエピソードで、80 エピソードの周期は**平均 36.6 実秒**、すなわちシミュレーション 36 秒に対し切り替えは**約 0.6 秒**である(`local/phase0-leave.jsonl` の `wall_seconds`)。**下の表は打ち切りの長さから引いた見積りであり、切り替えを 1 秒として置いてある。**

## 実測: 難易度に差を付けても決着しない

決着しないのが Hard 同士だからではないかを確かめるため、対戦者ごとに難易度を書き分けて測った。マップは同じ Islands、打ち切りはゲーム内 15 分である。

| 項目 | 値 |
| --- | --- |
| 難易度の指定 | 対戦者 0 に Impossible、対戦者 1 に Very Easy |
| エピソード数 | 24 |
| 決着 | 0 |
| 打ち切り | 24 |
| 軍事価値差の平均 | -0.011 |
| 軍事価値差の標準偏差 | 0.228 |
| 打ち切り時のユニット数 | 平均 103、標準偏差 11、範囲 71 から 117 |

**5 段の難易度差を指定しても、決着しないうえに軍事価値差の平均が 0 である。** 強いはずの側が有利にならない。

**この 24 エピソードは実行ログが `local/outcome-logs/` に残っており、上の値はどれも読み直せる。** 決着 0・打ち切り 24 も、軍事価値差の平均 -0.011 と標準偏差 0.228 も、それが要求する片側 328 エピソードも、ログから数え直した値と一致する。**上の[45 エピソード](#実測-内蔵-ai-同士は決着しない)とは別の集合であり、ユニット数の分布が違う**(平均 103 対 111、範囲 71 から 117 対 87 から 134)。打ち切り時間の指定が違うこの二つを、一つの標本として読んではならない。

**この結果は二通りに読める。区別できていない。** 一つは、対戦者ごとの難易度指定が効いていないという読みである。難易度は部屋が AI プレイヤーを作るときに `n.x` へ書き込まれるもので、こちらはその後に上書きしている。試合開始より前ではあるが、AI がその時点の値を内部に取り込んでいれば遅い。もう一つは、この地図とこの時間では難易度が結果に効かないという読みである。

いずれにせよ**現状、非対称な内蔵 AI の対戦を作る手段はない。** 部屋の設定 `config.f` は追加する全 AI に同じ値を与える([../game/05-match-control.md](../game/05-match-control.md))。対戦相手の集団は内蔵 AI の難易度ではなく、スクリプト方策の側で用意することになる([03-script-policy.md](03-script-policy.md))。

**副産物として、この 24 エピソードは対称な対戦の標本になった。** 上の軍事価値差の分布はここから取っている。

## 評価の手順

以上をまとめると次の形になる。

1. **相手を固定する。** 内蔵 AI の 1 段階か、凍結したスクリプト方策か、凍結した学習済み方策。相手が変われば数字は比較できない。
2. **設定を固定する。** マップ、開始クレジット、開始ユニット、収入倍率、霧、打ち切り時間。乱数種は固定しても試合を再現しないが、**どの種で取った数字かは報告に併記する。** 候補選びに使った種か、確かめに使った種かで、同じ数字の意味が変わるからである([最良として選ばれた差は、選択に使っていない実行で測り直す](#最良として選ばれた差は選択に使っていない実行で測り直す))。
3. **両方の方策を同じ条件で回す。** 片方だけを後から回すと、機材の状態の違いが差として現れる。
4. **採点の平均と標準偏差を出す。** 標準偏差から、その差を主張するのに必要なエピソード数を確認する。足りなければ回す。
5. **乱入込みで回す。** 学習も評価もスクリプト乱入者を注入した状態で行う([03-script-policy.md](03-script-policy.md))。人間は最終確認だけに使う。
6. **複数の候補から選んだものは、選択に使っていない実行で測り直す。** 選択に使った測定は候補を並べるためのものであって、差の主張ではない([最良として選ばれた差は、選択に使っていない実行で測り直す](#最良として選ばれた差は選択に使っていない実行で測り直す))。**測り直す種では基準線を同時に取り、方策の数字からそれを引いて報告する。**

### 両方の方策は交互に回す

手順 3 の「同じ条件で回す」は、**片方を全部回してからもう片方、ではなく、インスタンスの中で交互に回す**ことで満たす。順に回すと、二つの数字は方策の違いに加えて「その間に機材の状態が変わった分」だけ違う。交互なら、その差は両方に等しく乗る。

実装では、1 インスタンスが `方策の数 × エピソード数` 回のエピソードを回し、方策を順番に切り替える。

### 記録するもの

試合が再現しないため、**乱数種だけを記録しても不具合は再現できない**([../game/05-match-control.md](../game/05-match-control.md))。エピソードごとに次を残す。1 行 1 エピソードの JSON として、終了のたびに追記する。途中で止めた実行でも、そこまでが残る。

| 項目 | 用途 | 実装 |
| --- | --- | --- |
| 設定一式と相手の識別 | 比較可能性 | `settings` と `arm` |
| 採点とその内訳 | 主指標 | `standing` から再計算できる形で残す |
| 終局の一定時間前の盤面 | 重みの当てはめ | `before` と `before_seconds`。決着した試合の終局盤面は敗者が消えた後なので、重みを当てはめる問題としては易しすぎる |
| 決着か打ち切りか、決着なら勝者と時刻 | 重みの調整 | `winner` `timeout` `seconds` |
| 各層の決定回数と、契約の達成率 | どの層が効いたかの切り分け | `statistics` |
| 乱入者が起こした事象 | 除外すべき部隊の特定 | `interference`。事象の列と、触れられた部隊の一覧 |

**乱入の欄は実行の出来を測る数字ではない。** 事象の列は乱入者自身(`rwintel/control/intruder.py` の `Log`)が集め、エピソードの終わりに `interference` として記録へ移り、他の項目と同じ 1 行の JSON に入る。触れられた部隊の一覧を残すのは、後の学習実行がどの部隊の戦果を信号から落とすかを決めるためである([03-script-policy.md](03-script-policy.md))。人間の介入はこの欄には入らない。介入は起きたその瞬間に、そのとき見ていた盤面と対にして別の記録先へ書く必要があり([01-architecture.md](01-architecture.md))、エピソードの終わりの要約では盤面が失われるためである。

**採点の値そのものではなく素材を残す。** 重みは後から決まるものなので、素材を残しておけば過去の実行を新しい重みで採点し直せる。値だけを残すと、重みを変えるたびに回し直すことになる。**採点し直す口が `--weights` である**——`python -m rwintel.eval --from <journal> --weights 0.6,0.4,0.0` は、その journal を当てはめた重みで読み直す。これが無ければ当てはめた重みは報告されて捨てられるだけだった。

## 道具

方策の比較は `python -m rwintel.eval` である。制御プロセスを先に起動し、そこへゲームを接続するのは通常の実行と同じである。

```powershell
python -m rwintel.eval --instances 4 --episodes 3 --arm script --arm arm --map Lake --max-seconds 300
python -m rwintel.eval --instances 4 --episodes 3 --arm script --arm ops:local\operations.pt --intrude --map Lake --max-seconds 300
.\tools\windows\Start-RwAgents.ps1 -Count 4 -Speed 10
```

`--arm` が比較する方策である。`script` が階梯に任せたもの、姿勢の名前を渡すとその姿勢に固定したものになる。固定は人間が戦略層を引き取るための経路そのものであり([01-architecture.md](01-architecture.md))、比較のために作った仕掛けではない。**`ops:<パス>` を渡すと、学習済み作戦層をそのファイルから読み込み、鎖の残りをスクリプトに固定したアームになる。** これが作戦層を梯子と比べる経路であり、[04-learning.md](04-learning.md) の決闘が戦術層に対してすることの作戦層版である。戦術層はアリーナの交戦の上で測るが、作戦層は盤面全体と領域・タスクの選択なので試合単位でしか測れず、その測定はこの道具が行う。学習済みアームは網を 1 度だけ読み込み、全インスタンスの推論を 1 つの束ね器で束ねる(戦術の決闘と同じ配線)。**相手側がそこに居ないパラメータなら、真新しい方策を黙って採点せず異常終了する**([04-learning.md](04-learning.md) の [手順](04-learning.md#手順) の決闘と同じ理由)。**`strategy:<パス>` を渡すと、学習済み戦略層を同じ配線で読み込む**——鎖の残りはスクリプトに固定され、姿勢だけがその網のものになる。**`tactics:<パス>` も同じ配線で読み込める。この層の強さそのものは交戦アリーナの上で測るのであって試合では測らないが、鎖の下に置く層としては要る**——学習の実行は `--frozen tactics:<パス>` で学習済みの戦術層を下に凍結して上位層を鍛えられるのに、その上位層を手書きの戦術層の下で測れば、**鍛えた環境とは別の環境で測ったことになる。アームが運ぶ鎖は、その層が鍛えられた鎖でなければならない。** **そして `ops:<パス>+strategy:<パス>` や `tactics:<パス>+ops:<パス>+strategy:<パス>` のように `+` で繋ぐと、一つのアームが学習済みの層を何枚でも運ぶ。** これが無ければ、設計が言う「凍結した隣人に対して一層を学習させる」の後半——**下の層を実際に良くしたあとで、その上に層を積んだ鎖**——を測る経路が無かった。学習の実行側には `--frozen` があるのに、測定の側に対応するものが無かったのである。**繋いだアームは全ての層を読み、どれも学習しない**(rollout を持たない)ので、凍結と測定の違いは無い。**名前はファイル名の語幹を同じ `+` で繋いだものになる**ので、鎖のアームが片方の層だけのアームと journal 上で混ざることはない。**同じ層を二度名指したアームは異常終了する**——一方が決して打たないことになるからである。**隠れ幅はファイルから読む。** 三層の網はどれも特徴から隠れ幅への線形写像で始まるので、ファイルは自分の幅を名乗っている。以前はアームが既定の幅で網を組んでいたので、`--width` を上げて鍛えたパラメータは形が合わずに落ちた——**幅を掃引する選択肢はあるのに、それで鍛えたものを測る道が無かった。** 学習実行の `--frozen` も同じで、既定以外の幅の層は下に凍結できなかった。いまはどちらも最初の線形写像の形から幅を読む(構築作戦アリーナの `--tactics` が前からそうしていたのと同じやり方である)。**幅が合ったことが言えるのは「その層のパラメータである」ことだけであり**、特徴の意味が今のものであることは幅ではなく刻印が言う。**姿勢を固定したアーム(`defend` など)を同じ実行に並べると、「姿勢を選ぶこと」そのものの床が同じ相手の上で取れる**:固定は人間が層を引き取る経路そのものなので、それを床にすることは測定のために作った仕掛けではない。**`ops-concentrate` を渡すと、作戦層の行き先を戦略層が最も欲しがる領域へ上書きしたアームになる**——構築作戦アリーナで梯子を 0.08 から 0.10 上回り、取りに行くべき disc の 5 分の 1 を取る(梯子は 20 分の 1)アームの試合版である。**これを試合で測る理由は経済である**:収入は資源地点の上の採掘施設から来るので、**地面は経済の上流であり、この鎖が負けているのは経済である**(480 試合で収入 35.5 対 77.9、立っている価値 9,157 対 25,662)。**アリーナの優位が試合へ乗るかどうかは、その後に測ってある。乗る。** Lake・打ち切り 300 秒・内蔵 AI 一体(難易度 1)・乱入込み、鎖はどれもスクリプトで違うのは作戦層だけ、アームごと 96 試合で、採点は `ops-concentrate` が -0.471、手書きの梯子が -0.536、`ops-pin` が -0.539 である。**`ops-concentrate` − `script` = +0.065 は、上の二標本の式が要求する片側 91 試合に対して 96 試合あり、経済成分も -0.369 から -0.315 へ動いた。** **同じ実行の `script` − `ops-pin` = -0.004 は片側 19,441 試合を要求する——手書きの梯子の丁寧な選択は、何も選ばない配備と区別が付かない**([../record/04-operations.md](../record/04-operations.md))。**`ops-pin` を渡すと、作戦層を最小番号の合法領域とタスクへ一定に固定した配備にする**——アリーナの `--pin` の試合版であり、網も読み込みも要らない。何も選ばない自明な配備なので、学習済みや模倣の作戦層はこれを床として読む(領域マスクは常に 9、タスクマスクは常に 2 あって行動空間はつぶれないのに、28 パーセント違う選び方が同じ成績になる、その「選択そのものの価値」を測るための下限である)。**学習済みアームをどう読むかは実行が言う。** 既定は抽選(分布から引く)であり、これまでの試合測定はすべてその読みで取ってある。`--greedy` を渡すと全学習アームが確率最大で打つ。**構築作戦アリーナの測定ランナーは確率最大で読む**ので、二つの場の数字は同じ読みのものではない——どちらが強いかではなく、どちらの読みで取ったかを揃えないと比べられない、という意味である(抽選の税は未解決の問いである。[../record/06-open-questions.md](../record/06-open-questions.md))。アームは読み込んだファイルの名で記録される。この床が実際にいくらだったかは [../record/04-operations.md](../record/04-operations.md) にある。`--episodes` は**方策ごと**の回数なので、最初の例は 1 インスタンスあたり 6 エピソード、合計 24 になる。**乱入者は `--intrude` が全アームへ一様に付ける**ので、学習済みアームだけに乱入を組み込むことはしない([03-script-policy.md](03-script-policy.md))。

エピソードごとの採点、その内訳、標準偏差、そこから決まる必要エピソード数、二つの方策の差とそれを主張するのに足りているかを報告する。実行のたびに全エピソードが JSON 行として残るので、後から重みを変えて採点し直せる。

```powershell
python -m rwintel.eval --from local\episodes\lake.jsonl
```

**作戦選択そのものを比べる道具は別にある。** 試合の中の作戦層は上の `--arm ops:<パス>` で梯子と比べるが、[04-learning.md](04-learning.md) の構築作戦アリーナの上では `rwintel.learn.ops_run` が複数のアームを**同じ盤面の上で**回す。`--our` は繰り返せる指定で、`script`(両側とも手書きの鎖、すなわち自己対戦ゼロ)、`pin`(全部隊を最小番号の合法領域とタスクへ送る、選択を一つもしない層)、`massed`(手書きの梯子から「自軍の戦力が既に立っている領域が受ける割引」だけを外したもの。**この場ではその割引がもともとほぼ 0 なので、測ると梯子と同じ決定を下す。集中のアームではなく一項のアブレーションである**)、`narrow`(手書きの梯子から「**戦略層が優先度を置いた領域は、ドクトリン自身の絞り込みが落としていても候補に加わる**」規則を外したもの。加入が何点ぶんかを測るためのアブレーションである)、`concentrate`(ドクトリンが選んだタスクは残し、**行き先だけを戦略層が最も欲しがる領域へ上書き**したもの。選択を丸ごと置き換えるので、これが本物の集中である)、`wanted:<重み>`(手書きの梯子はそのままに、**戦略層の要求だけを、梯子が自分で読む項に対して重み付けし直したもの**。`wanted:3` なら 3 倍。**加入の版が梯子の指す先を動かさなかったのを受けて足したアームであり、疑っているのは候補集合ではなく項の尺度である**:優先度は 1 を超えないのに、資源 4 の地面は 0.6、保持している地面の上の敵戦力はさらに 0.3 を持つので、候補に加えても収入を産まない係争点は静かな鉱山に採点で負ける。**行き先を置き換える `concentrate` と違い、項はすべて読まれたままで、動くのは要求の重さだけである。** 重みは省略できず、裸の `wanted` は拒む——既定の重みは 1.0 なので、それは `script` アームの別名になるからである。負の重みも拒む。journal には `ops-wanted-<重み>` と書かれる)、`learnt`(`--load` から読む学習済みの網、確率最大で打つ。**`learnt:<パス>` と書けば自分のパラメータを持つので、一つの実行が同じ訓練線の二世代を同じ盤面の上に載せられる。** その形では journal に `ops-learnt-<ファイル名の語幹>` と書かれ、裸の `learnt` の `ops-learnt` と混ざらない)の七つを取る。アームはインスタンスの中で交互に回り、**盤面は全アームが打ち終わるまで進まない**ので、1 回の実行がそのまま対にした比較になる。`--episodes` は**アームごと**の本数である。実行の最後に、アームごとにプールした side score と、**すべての 2 アーム組について盤面ごとに対にした差**が出る。

```powershell
python -m rwintel.learn.ops_run --instances 8 --episodes 10 --map Hills --our script --our pin --our massed
python -m rwintel.learn.ops_run --instances 8 --episodes 10 --map Hills --seed 60001 --our pin --our learnt --load local\ops-arena.pt
.\tools\windows\Start-RwAgents.ps1 -Count 8 -Speed 10
```

**アームごとの平均の読み方はアームによって違い、報告はそれを名指しする。** `script` アームの平均は自己対戦ゼロであり、2 標準誤差の外へ出ていれば盤面が傾いているので、見つけて直すまでその上の測定は信用しない。`script` 以外のアーム(`pin`・`massed`・`narrow`・`concentrate`・`wanted:<重み>`・`learnt`)の平均は「そのアームが手書きの側からどれだけ離れて立っているか」であって傾きではないので、そこに傾きの警告を出すことはしない。**`--our learnt` は `--load` が無ければ異常終了する。** 読み先が無いまま走れば、真新しい網を学習済みアームの名前で採点して journal に残すことになり、後からその二つを見分ける手段が無いからである(決闘の `--load` と同じ理由)。

**journal から後で対を読み直すのが `rwintel.learn.ops_compare` である。** ゲームを起動せず、journal だけを読む。二つのファイルでも、複数のアームを持つ一つのファイルの中の二つのアームでもよい。対にする鍵はエピソードが記録している `board`、すなわちその盤面を引いたアリーナ種である(**それを持たない古い journal は、種・インスタンス・エピソード番号からの派生で鍵を作る。その派生が正しいのはアームが 1 本の実行だけである**)。**欄が有るかどうかは、値ではなく存在で見る。** 盤面の名前は引いた種そのものなので 0 も正当な名前であり、真偽で見ていたころは**種 0 から引いた盤面だけが「欄を持たない古い journal」と読まれ、多アームの実行では正しくない派生へ落ちていた**——一つの実行の中で、その 1 枚だけが他の盤面と違う規則で対にされることになる。**エピソード設定と抽選設定が一つでも違う二つは、対にすることを拒否する**——それは二つのアームの差ではなく二つのアリーナの差だからである。一つの盤面が二度記録されている journal も、どちらのエピソードを採るか決める手立てが無いので、その盤面を両方落として言う。報告は、アームそれぞれ単独の平均と散らばり、盤面ごとに対にした差とその 2 標準誤差、三つの散らばりと二つのアームの相関、そしてその差が何対を要するかである。

```powershell
python -m rwintel.learn.ops_compare local\episodes\ops-script-pin-massed.jsonl --first-arm ops-script --second-arm ops-pin
python -m rwintel.learn.ops_compare local\episodes\ops-learnt.jsonl local\episodes\ops-pin.jsonl
```

**macOS ではこれらを `tools/macos/learn-run.sh` を通して起動する。** 上の Windows の例は制御プロセスとゲームを人が二つの窓で手で立ち上げるが、macOS ではゲームはコンテナの中にあり、二つの寿命を結ぶものが無い。`learn-run.sh` は `--` の後のホストのコマンドをそのまま起動し、コンテナをその相手として立ち上げ、ホストのコマンドがエピソードを終えた時点でコンテナを止める。コンテナはホストを別ホストとして見るので、ホスト側は `--host 0.0.0.0` で待ち受ける。**`ops_compare` はゲームに触れないので、これは要らない。**

```bash
tools/macos/learn-run.sh --count 8 --speed 10 -- \
    python -m rwintel.learn.ops_run --host 0.0.0.0 --instances 8 --episodes 10 --map Hills --our script --our pin --our massed
```
