# 速度と並列数

学習に使えるサンプル収集速度を決めるものと、その測り方を記す。この速度が強化学習の計画全体の制約になる。値そのものは機材と試合の局面で変わるので、ここには振る舞いと粗い大きさだけを書き、正確な値は `python -m rwintel.runtime probe` と `outcomes` が実行時に報告する。

## 1 フレームの費用

ゲームスレッドが 1 フレームで行う仕事は三つに分かれる。

- **描画。** 表示装置の無い環境でも 10x10 のウィンドウへ描いており、費用は画素ではなく、ユニットごとの描画呼び出し、毎フレームのクリア、画面の入れ替えにかかる。スキルミッシュの序盤から中盤では、シミュレーションそのものより重い。**既定で止めてある**([02-runtime.md](02-runtime.md) のフレーム層)。止めてもシミュレーションは変わらない([../game/01-internals.md](../game/01-internals.md) の描画の経路)。
- **シミュレーション。** 生存オブジェクトの数に応じて重くなる。試合の終盤、ユニットが数百体になると 1 ステップの費用は序盤の何倍にもなる。
- **フレームの待ち。** ゲーム自身の時計ではフレームレートの上限まで `Display.sync` が待つ。この待ちは `Thread.yield` を回す空回りで、手の空いた CPU があるとそれを使い切る。

描画を止めると、残りはほぼシミュレーションだけになる。

## 二つの時計

[../game/02-launch.md](../game/02-launch.md) のとおり、ゲーム自身の時計では速度と忠実度が直交する二つのつまみになる。このプロジェクトはそれに加えて、実時間から切り離した固定ステップの時計を持つ。

**固定時計(既定)** は全フレームをちょうど `--step-ms`(既定 25 ミリ秒)進め、フレームの上限を外す。1 ステップの粗さは負荷に左右されず、1 秒あたりに進むゲーム内時間は CPU が許す限り上がる。**処理量の単位はフレームではなくゲーム内時間になり、各インスタンスは論理 CPU をほぼ 1 個使い切る。** 2 プロセスのロックステップの試合だけは固定時計が効かず、wall 時計で走る([02-runtime.md](02-runtime.md))。 25 ミリ秒は通常の 30fps のプレイより細かく、制御の周期をすべて割り切る([05-interface.md](05-interface.md) の周期の刻み)。

**wall 時計** はゲーム自身の時計で、倍率 `--speed` とフレームレートの上限 `--fps` で決まる。1 ステップは平均 `1000 * H / fps` ミリ秒だが整数ミリ秒で割れ、CPU が足りなくなると、まずフレームレートが下がってステップが粗くなり、さらに足りなくなると倍率そのものが保てなくなる。上限を外しても、1 ミリ秒を切るフレームは時間を進めないので速くはならない。

## 並列数との関係

**固定時計では、並列数の最適点は論理 CPU の数である。** 各インスタンスが CPU を 1 個使い切るので、それより増やしても同じ CPU を分け合うだけで、合計は増えずメモリだけが増える。制御プロセスと最適化器も同じ CPU を使うので、それらを動かすときはその分だけ減らす。

**メモリは 1 インスタンス 0.6GB 前後を使う。** wall 時計では 1 インスタンスが論理 CPU 1 個に満たないため並列数を CPU の数より上げる余地があり、そこではメモリが先に尽きうる。WSL2 では割り当てメモリが既定でホストの半分なので、`.wslconfig` の `memory=` で上げる。

合計の速さを決めるものは、時計によって違う。

- **wall 時計では、合計は倍率と並列数の積で頭打ちになる。** 各インスタンスは倍率の分しか進まないので、局面によらず合計はほぼ一定で、CPU には余りが残る。試合を切り替える間はゲーム内時間が進まないので、短い試合を続けて回すと合計はその分だけ下がる。
- **固定時計で描画を止めると、合計は CPU の数とシミュレーションの費用で決まる。** 並列数を論理 CPU の数より上げても合計は伸びない(上の並列数の最適点)。1 ステップの費用は生存オブジェクトの数で決まるので、同じ機材でも局面によって数倍から一桁違う。ユニットの少ない序盤から中盤で打ち切るスキルミッシュがいちばん速く(試合の切り替えを含めても)、ユニットが数百体になる終盤がいちばん遅い。終盤でも、描画ありの wall 時計を倍率 10 で回す従来の構成より速い。

## 制御プロセスとの関係

制御エージェントのインスタンスは、固定時計では戦術周期ごとに制御プロセスの答えを待つ([05-interface.md](05-interface.md) の 1 周期の遅れを固定する)。したがって**その処理量は、シミュレーションの速さと制御プロセスの答えの速さの遅い方で決まる。** 制御プロセスは Python の 1 プロセスで全インスタンスに答えるので、並列数を上げるとこちらが先に頭打ちになりうる。CPU に余りがあるのに合計が伸びないときは、測定のゲームを複数の制御プロセスに分ける(`run --controls`、[02-runtime.md](02-runtime.md) の制御プロセスを分ける)。合計は本の数とともに、CPU を使い切るところまで伸びる。推論はインスタンスをまたいでまとめて評価し、決定中のスレッドが揃った時点で評価して待ちを足さない([08-learning.md](08-learning.md) の推論の集約)。学習の実行は最後に、1 インスタンスの倍率、合計の倍率、実時間 1 秒あたりの決定数を報告する。

交戦アリーナでは、上限を決めるのはシミュレーションではなく制御プロセスであり、1 インスタンスの速さは内蔵 AI だけの試合より遅い。固定時計では wall 時計より多くの決定を捌き、wall 時計では答えの間に合わない周期が出るのに対し、固定時計ではどの周期にも前の周期への答えが効く。

## 学習器をグラフィックスカードに分けたとき

記録した決定だけを読む学習(`python -m rwintel.learn offline`、[08-learning.md](08-learning.md) のオフライン学習)は、ゲームにも制御プロセスにも触れない。**この形では学習の速さはサンプルを集める速さと切り離され、律速は引き続きゲームのシミュレーションによる収集である。** 学習の側は、データを丸ごとカードに置き(状態は半精度)、大きなミニバッチと bf16 の前進で回す。ホストのメモリを使うのは読み込みの間だけで、戦術層の集合の状態は実行ごとにキャッシュしたファイルをメモリに写像して読む。集合の状態は 1 決定あたり 600 個の数で、半精度で 1.2KB になる。

**行動器と学習器を分けたループ(`learn online`、[08-learning.md](08-learning.md) の行動器と学習器を分ける)でも、学習器はゲームを待たせない。** 行動器のゲームの処理量はこれまでどおりシミュレーションと答えの速さの遅い方で決まり、学習器の更新の速さが効くのは、新しい版が行動器に届くまでの間隔だけである。その間隔は、学習器が版を出す更新の回数(`--publish-every`)、行動器がサイドカーを見る間隔(`--reload-seconds`)、行動器の記録が断片になって学習器に読まれるまでの決定の数(`--shard-decisions`)と学習器がそれを探す間隔(`--rescan-seconds`)で決まる。学習器と行動器が同じカードを使うときは、まとめ役の呼び出しと学習器の更新がカードを分け合う。そのとき各々はカードのメモリの決まった割合だけを持ち(`learn online` では学習器 0.5、行動器 0.1、`--card-share`)、行動器は集合の網をカードの上で回す。

**推論の費用は網の種類で桁が違う。** 集合の網はパラメータが平らな網の数倍から数十倍あり、トークンごとに注意を計算するので、1 回の呼び出しが呼び出しの手間ではなく演算で決まるようになる。CPU では 1 決定あたりの費用がバッチを大きくしても下がりにくく、平らな網よりおよそ一桁高い。CPU だけの制御プロセスでは、集合の網を蒸留した今の大きさの平らな網(`offline --method distill`)を使えば、制御プロセス 1 本で捌けるインスタンス数は今と変わらない。**そのため集合の網のファイルは、グラフィックスカードがあればそこで回す**([08-learning.md](08-learning.md) の網の大きさ)。

**グラフィックスカードでは、小さなバッチの呼び出しの費用がほぼ起動の手間で決まり、バッチを大きくしてもしばらくは長くならない。** 1 件だけの呼び出しは CPU より遅いが、まとめるほど 1 決定あたりが安くなる。集合の網では、バッチがある大きさを超えると呼び出しが演算で長くなる。まとめ役の窓と上限はデバイスごとに持ち(`inference.LIMITS`)、カードの組は `learn bench` から一つの規則で読む。上限は、1 回の呼び出しが 1 件の呼び出しの 2 倍以内に収まる最大のバッチの大きさで、窓は CPU と同じ 4 ミリ秒にしておき、1 件の呼び出しがそれより長いときだけその長さにする([08-learning.md](08-learning.md) の推論の集約)。カードの組は、カードの上で多数のゲームに打たせる網である戦術層の集合の網について、空いたカードでこの規則が読む組であり、窓も上限も CPU と同じになる。カードを他の仕事と分け合っているときの `bench` は 1 件の呼び出しを長く見せるので、組を決める `bench` はカードが空いているときに回す。

## ソフトウェア描画のスレッド数

表示装置の無い環境では、各インスタンスのウィンドウを Mesa のソフトウェア描画(llvmpipe)が受け持つ([02-runtime.md](02-runtime.md))。llvmpipe は既定でプロセスごとにコア数だけの描画スレッドを起こすので、十数並列ではそのスレッドがシミュレーションと同じコアを奪い合う。道具は既定で各インスタンスの描画を 1 スレッドに制限する(`--render-threads 1`、環境変数 `LP_NUM_THREADS`)。描画を止めている既定の構成では、描画スレッドが働くのは主にマップの読み込みでテクスチャを作るときであり、制限が効くのは `--draw` のときである。

## 学習計画への意味

合計の速さが、その機材でのサンプル収集予算である。内蔵 AI やスクリプト方策だけで回す測定は、固定時計の数字がそのまま予算になり、1 時間の実行でゲーム内の数百時間から数千時間が回る。制御プロセスが方策を回す実行はそれに加えて答えの速さに縛られる。

それでも RTS の強化学習研究が前提にする規模には一桁から二桁足りない。したがって**ゼロからの強化学習だけで方策を得るのは現実的ではない**。手書きのスクリプト方策を先に作り、それを骨格と教師と評価基準に使う順序が妥当である。一方で、方策の評価、スクリプト方策の調整、そのスクリプト方策からの模倣学習用データの生成には十分な速度である。人間のリプレイからの模倣を縛るのは速度ではなく、人間が遊んだ量である([04-model-design.md](04-model-design.md))。

### この予算が縛るのは戦術より上の層である

上の数字は「試合を最初から最後まで回す」ことを前提にしている。試合全体を通してしか帰結が現れない判断、すなわち戦略・内政・編成・作戦を学習する層は、この予算に縛られる。

一方、交戦の巧拙を学習する戦術層は試合を回す必要がない。正規のコマンド経路で任意の交戦状況を構築でき([../game/04-actions.md](../game/04-actions.md) のシステム命令と [../game/05-match-control.md](../game/05-match-control.md) の試合設定)、1 交戦がゲーム内 10 秒から 60 秒で閉じる。同じ実時間から取れるサンプル数は試合単位の数字と桁で違う。

**したがって試合単位の予算は、モデル全体の予算ではなく、戦術より上の層の予算として読む。** 層の構成と環境の作り分けは [04-model-design.md](04-model-design.md) に記す。

## 上限を上げる手段

- **コアを増やす。** 固定時計の合計はコア数に比例するため、これが本質的な手段である。表示装置の無いマシンでは仮想ディスプレイとソフトウェア描画で動く([02-runtime.md](02-runtime.md))ので、GPU の無いマシンにもそのまま広げられる。観測と行動の伝送は TCP なので、制御プロセスを別マシンに置く形にも広げられる([05-interface.md](05-interface.md))。
- **制御プロセスの答えを速くする。** 制御エージェントを使う実行の上限はここにある。
- **エピソードの切り替えを減らす。** 切り替えの大半はマップの読み込みで、シミュレーションが速くなった分だけ割合が増えた。短いエピソードを多数回すより、長いエピソードやアリーナのように盤面を作り直す形の方が効率がよい。

## 測り方

計測は他の負荷がない状態で行う。**背景で別の処理を走らせたまま取った値は大きく歪む。** 最初の 30 秒程度は実行時コンパイルの影響で値が変動するので、計測時間は 60 秒以上取る。`probe` は各インスタンスの最後の計測区間を集計に使う。

```bash
python -m rwintel.runtime probe --count 16 --seconds 90
python -m rwintel.runtime probe --count 16 --seconds 90 --clock wall --speed 10 --draw
python -m rwintel.runtime outcomes --count 16 --episodes 5 --map Islands
```

`--map` を付けない `probe` はメニュー背景の戦闘を負荷とし、負荷が一定なので構成どうしの比較に向く。`--map` を付けた `probe` の最後の区間は、固定時計ではその時点の局面の重さを映すだけで、エピソードの切り替えをまたぐ区間は数えない。試合を回した実効の速さは、終えたエピソードのゲーム内時間の合計を実時間で割ったもので、`outcomes` がこれを `throughput` として報告し、所要時間の見積もりにも使う。報告は `local/logs/<道具>/<日時>/summary.txt` にも残る。

交戦アリーナの速度は、学習の実行が最後に報告する。1 インスタンスの倍率と合計の倍率、ゲーム内 1 分あたりの交戦数と決定数、実時間 1 秒あたりの決定数である。

```bash
python -m rwintel.runtime run --count 16 -- learn duel --episodes 3
```

## 分かっていないこと

- 長時間の連続実行における熱による低下の影響。
- 8 人用や 10 人用の大きなマップでの負荷が、2 人用や 4 人用のマップと同じ振る舞いになるか。
- 並列数を論理 CPU の数から減らしたときに、SMT の相方が空くことで 1 インスタンスあたりがどれだけ速くなるか。
