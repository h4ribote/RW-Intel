# 方策の評価

二つの方策のどちらが強いかを判定する手順である。**採点、必要エピソード数、エピソードごとの記録、方策の差し替えによる比較のすべてが実装済みである。** 実物は `rwintel/eval` にあり、`python -m rwintel.eval` で動く。ここに書くのは方式の決定と、それを支えるゲームの性質である。

評価を早く決める理由は [04-model-design.md](04-model-design.md) にある。同一の乱数種と設定を与えても試合は再現しないため([../game/05-match-control.md](../game/05-match-control.md))、片方の方策を差し替えて同じ展開で比べることができない。**評価は最初から多数エピソードの平均として設計する必要があり、以降のすべての判断がこれに依存する。**

## 内蔵 AI 同士は決着しない

4 人用マップ Islands に内蔵 AI を 2 名だけ残して対戦させ(開始クレジット 4000、建設機 1 体、収入倍率 1.0、視線の霧)、ゲーム内 25 分で打ち切ると、**エピソードは一つ残らず打ち切りで終わる。** 生存チームは最後まで 2 つのままで、勝者が決まらない。同じ難易度の内蔵 AI 同士は、序盤に取った資源地点を守り合い、前線が動かなくなる。

**難易度に差を付けても決着しない。** 対戦者ごとに Impossible と Very Easy を書き分け、ゲーム内 15 分で打ち切っても、決着するエピソードは無く、軍事価値差の平均は 0 のそばにある。強いはずの側が有利にならない。

この結果は二通りに読めて、区別できていない。一つは、対戦者ごとの難易度指定が効いていないという読みである。難易度は部屋が AI プレイヤーを作るときに `n.x` へ書き込まれるもので、こちらはその後に上書きしている。試合開始より前ではあるが、AI がその時点の値を内部に取り込んでいれば遅い。もう一つは、この地図とこの時間では難易度が結果に効かないという読みである。

いずれにせよ**現状、非対称な内蔵 AI の対戦を作る手段はない。** 部屋の設定 `config.f` は追加する全 AI に同じ値を与える([../game/05-match-control.md](../game/05-match-control.md))。対戦相手の集団は内蔵 AI の難易度ではなく、スクリプト方策の側で用意することになる([06-script-policy.md](06-script-policy.md))。

これを測るのが `python -m rwintel.runtime outcomes` である([道具](#道具))。

**スクリプト方策と内蔵 AI の試合は、打ち切りを長くすると決着する。** ゲーム内 15 分で打ち切ると決着はまれだが、45 分まで延ばすと、難易度 0 以上の相手との試合の多くが決着する。決着はどれもスクリプト方策の負けである。決着した試合は、打ち切り時の採点の重みを合わせる材料になる([重みの決め方](#重みの決め方))。

## 帰結: 勝敗だけを主指標にはできない

勝率は二値であり、その標準誤差は `sqrt(p(1-p)/n)` である。勝率 0.5 のあたりで差 `delta` を有意水準 5 パーセント・検出力 80 パーセントで検出するには、片側あたり `7.85 * 2 * 0.25 / delta^2` エピソードが要る。係数 7.85 は `(1.96 + 0.84)^2` であり、`rwintel/eval/sampling.py` の `SIGNIFICANCE_POWER_FACTOR` である。

| 検出したい勝率差 | 片側あたりのエピソード数 |
| --- | --- |
| 0.05 | 1570 |
| 0.10 | 393 |
| 0.15 | 175 |
| 0.20 | 99 |
| 0.30 | 44 |

数字そのものは扱える大きさに見える。**問題は、この観測が一部の試合でしか得られないことである。** 内蔵 AI 同士の試合は決着せず、スクリプト方策の試合も多くは打ち切りで終わる。勝率だけでは、ほとんどのエピソードが何も言わない。

したがって**主指標は打ち切り時の盤面を採点する連続量とする。** 勝敗は、それが付いたときに採点を飽和させる形で組み込む。

## 採点

エピソードの終わりに、自軍から見た優劣を `-1` から `+1` の範囲で採る。**採点は勝敗の期待値として設計する。** 決着した試合は結果そのもの、打ち切られた試合は盤面から予測した `2 P(勝ち) - 1` であり、両者が同じ尺度に乗る。

```
決着したなら  score = +1(勝ち) または -1(負け)
打ち切りなら  score = tanh((w_m * m + w_e * e + w_x * x + w_c * c) / 2)
```

`tanh(z / 2)` はロジスティック関数 `P = 1 / (1 + exp(-z))` を `2P - 1` に写したものである。重みは決着した試合から合わせる([重みの決め方](#重みの決め方))。**重みを採用するまでの既定は、軍事価値差だけの線形の採点 `clamp(m, -1, +1)` である**(`rwintel/eval/scoring.py` の `OPENING_WEIGHTS`、`--weights opening`)。いまはこの初期値で採点している。採用できる重みがまだ無い理由は [重みの決め方](#重みの決め方) にある。

| 記号 | 量 | 定義 | 出所 |
| --- | --- | --- | --- |
| `m` | 軍事価値差 | (自軍の現有価値 - 敵の現有価値) / 両者の合計 | 価格の総和([06-script-policy.md](06-script-policy.md)) |
| `e` | 経済差 | (自軍の収入 - 敵の収入) / 両者の合計 | `n.v()` |
| `x` | 交換比 | (自軍の撃破数 - 自軍の喪失数) / (自軍の撃破数 + 自軍の喪失数)。ユニットと建物の数であって価格ではない。まだ何も失われていなければ 0 | `l.bY.a(player)` の `c` `d` `f` `g` |
| `c` | 手持ちの差 | (自軍の未使用クレジット - 敵の未使用クレジット) / 両者の合計 | プレイヤーのクレジット |

いずれも比であり、試合の長さやマップの大きさで尺度が変わらない。「敵」は量ごとに、その量で最も大きい相手をとる。三者以上の試合で、弱い第三者が平均を甘くしないようにするためである。**素材はすべて集計値から O(1) で取れる**ので、採点自体は費用にならない([../game/03-observation.md](../game/03-observation.md))。エピソード終了時に、陣営ごとのユニット数・現有価値・収入・撃破数・喪失数・クレジットがゲーム側から届く。クレジットを持たない古い記録では `c` は 0 と読む。

### 対戦者の判定

**ゲームは、誰も使っていないスロットのチームも最終状況に並べる。** 2 人用マップでもチーム 2 から 7 までが現れる。部屋は空きスロットにも AI のプレイヤーを作り、開始クレジットを配るが、出撃地点の無いそのプレイヤーは何も持たず何もしない。**ゲーム側は、ユニットを持ったことも、収入・撃破・喪失も無いプレイヤーのクレジットを、チームの合計に足さない。** そうしたプレイヤーは試合に加わった陣営と同じチームに入ることがあり、足すとその陣営の手持ちが開始クレジットの分だけ水増しされるからである。したがって誰も使っていないスロットのチームの行はすべて 0 になる。試合に加わった陣営は、盤面から消えた後も少なくとも喪失が数えられているので、この形にはならない。

したがって**ユニット数・価値・収入・撃破・喪失のいずれかが 0 でない陣営だけを対戦者とする**(`scoring.contestants`)。クレジットは判定に使わない。空きスロットのクレジットを数えていた記録にも同じ規則が当たるようにするためである。空きスロットを対戦者に数えると、「最も大きい相手」の値が 0 に引かれ、負になり得る量の比が片側にだけ張り付く。判定は制御側で行うので、過去の記録を採り直しても同じ規則が当たる。

### 交換比は自軍の数字だけで取る

**二陣営の対戦では、自軍の撃破数は相手の喪失数そのものである。** したがって、自軍の `撃破 - 喪失` と相手の `撃破 - 喪失` を比べる形にすると、両者は符号だけが逆の同じ値になり、比の分母が 0 になる。交換比はそうせず、自軍の撃破を自軍の喪失と比べる。こうすれば 1 対 1 でも情報を持ち、値は -1 から +1 に収まる。

### 重みの決め方

**重みは机上で決めず、決着した試合から合わせる。** 採点は勝敗の**予測**であってほしい。勝敗が付かない試合で「もし続けたらどちらが勝つか」を測るのが目的であり、そのための重みは実際の勝敗から学ぶのが筋である。

**合わせるのは終局時の盤面ではなく、終局の一定時間前の盤面である。** 決着した試合の終局時には、敗者は既に盤面から消えている。その盤面ではどの項も勝者を指すので、重みを合わせる問題として意味をなさない。採点を使う場面はまだ両者が立っている盤面であり、合わせる盤面もそうでなければならない。

そのために**エピソード記録は試合の途中の盤面を持つ。** ゲーム側は通常のエピソードの間、一定のゲーム内時間ごとに全陣営の最終状況を送り(既定は 30 秒ごと、`EpisodeSettings.standing_seconds`)、制御側はそれを対戦者だけに絞って記録の `history` に残す。これは方策には渡さない。霧に関係なく全陣営を集計した値だからである。アリーナのエピソードは試合として採点しないので、送らせない。

合わせ方は切片の無いロジスティック回帰である(`scoring.fit_weights`)。決着した試合ごとに、終局の既定 60 秒前以前で最後の盤面を取り、その成分から勝敗を予測する。

- **切片を置かないのは、互角の盤面を 0 と読ませるためである。** 相手の強さは採点の外にある。同じ相手に対するアームの比較では、定数のずれは差に現れない。
- **このモデルは盤面について奇関数なので、負けも勝ちと同じだけ情報を持つ。** 負けた試合は、相手から見れば勝った試合である。決着が片方の結果に偏っていても、重みの向きは合わせられる。大きさについては下の分離の問題がある。
- 係数の 2 乗に小さな罰則を付ける。勝敗を完全に分ける盤面の集まりで係数が発散しないようにするためであり、一度も動かない成分の係数は 0 に留まる。

報告は、合わせた重みに加えて、その盤面での的中率と、5 分割の交差検証で合わせに使わなかった盤面での的中率を出す。終局の 30、60、120、240 秒前それぞれで合わせた結果も並べる。

**すべての盤面の勝敗を当ててしまう重みは、勝率を言わない。** その盤面の集まりは勝敗で完全に分かれており、重みを何倍にしてもより自信を持って当たるだけである。データが決めるのは重みの向きだけで、大きさは罰則が決めている。報告はこれを `SEPARATED` と示し、`--fit-out` はその重みを書き出さない。較正には、盤面がまだ勝者を言っていなかった試合、つまり終局前の盤面で優勢だった側が負けることもある試合が要る。

**合わせた重みは、選択に使っていない実行で確かめてから採用する。** 手順は [最良として選ばれた差は、選択に使っていない実行で測り直す](#最良として選ばれた差は選択に使っていない実行で測り直す) と同じである。ある乱数種の実行で合わせ、別の乱数種の実行でその重みの的中率を測る。採用した重みは `rwintel/eval/weights.json` に置き、これがある限り既定の採点になる。

**いまは採用した重みが無い。** スクリプト方策が内蔵 AI と戦って決着する試合は、難易度 -1 から 2 のどれでもスクリプトの負けであり、終局の数分前の盤面が既に勝敗を分けている。この集まりから決まるのは、軍事価値差・経済差・交換比が正、手持ちの差が負という向きだけである。手持ちの差が負に効くのは、クレジットを溜めている側は稼ぎを戦力に変えていないからである。勝ち負けが入り混じる対戦(スクリプト方策どうしを一つの試合で戦わせる、あるいはスクリプト方策が勝てる相手を作る)で決着した試合が集まるまで、既定は初期値のままとする。

### 軍事価値差の散らばり

軍事価値差 `m` は、打ち切り時に生存している完成ユニットの価格を陣営ごとに合計し、差を合計で割った値である。内蔵 AI 同士の対称な対戦で、**平均はほぼ 0、標準偏差はおよそ 0.23** になる。平均が 0 のそばにあることが、この指標が対称な対戦で偏らないことを示している。陣営の入れ替えや地形の偏りが混じっていれば、ここに出る。

### 連続量に必要なエピソード数

標準偏差を `sigma`、検出したい差を `delta` とすると、片側あたり `7.85 * 2 * sigma^2 / delta^2` エピソードである。`sigma = 0.23` なら次のようになる。

| 検出したい軍事価値差 | 片側あたりのエピソード数 |
| --- | --- |
| 0.05 | 333 |
| 0.10 | 84 |
| 0.20 | 21 |

**これが評価を連続量で行うことの利益である。** 勝率で同じ土俵に立とうとすると、ほとんどの試合が決着しないので観測が得られない。盤面の採点は毎エピソード必ず得られる。実時間は [エピソードあたりの費用](#エピソードあたりの費用) と並列数で決まり、`outcomes` と `rwintel.eval` は測った散らばりからこの数と所要時間を自分で報告する。

**上の値は軍事価値差という一つの項の散らばりである。** 採用した重みでの採点は尺度が違うので、その散らばりと必要数は `rwintel.eval` が実行ごとに測って報告する。

### 二つ目の場合: 交戦の成績

同じ算術が、[08-learning.md](08-learning.md) の交戦アリーナにも当たる。**単位が試合ではなく交戦 1 件で、量は軍事価値差ではなく交戦の成績である。** 成績は相手が失った価値の割合から自分が失った割合を引いたもので、反対称であるから両側を同じ層にした基準線の平均は 0 でなければならない。散らばりは、生き残りを値段まるごとで数える疎な読みで 0.55 から 0.58、残り体力で割り引く読みで 0.48 から 0.52 である。

| 場合 | 単位 | 散らばり | 0.05 の差に要る単位数(片側) |
| --- | --- | --- | --- |
| 試合の軍事価値差 | エピソード | 0.23 | 333 |
| 交戦の成績(疎な読み) | 交戦 | 0.57 | 2041 |

**散らばりは試合の倍以上あるのに、費用は 1 桁以上安い。** 240 秒のエピソードが平均 6 から 7 交戦を生み、そのエピソードが固定時計では実時間十数秒で終わるためで、十数並列なら毎秒数件の交戦が出る。**アリーナでは、散らばりが大きいことは予算の問題にならない。** 問題は差の側が小さいことであり、そちらは回す量では解けない。

**上の式に入れてよいのは独立に引かれた交戦だけである。** アリーナはエピソードごとに乱数種を作り直し、そこへインスタンス番号とエピソードの周回数の両方を織り込んでいる([08-learning.md](08-learning.md) の [エピソードごとに交戦を引き直す](08-learning.md#エピソードごとに交戦を引き直す))。インスタンス番号だけから作ると、あるインスタンスの全エピソードが同じ交戦の列を引き直し、件数で割った区間が引かれた交戦の種類で割った区間より数十倍狭く出る。

**同じ実行の中で比べるものは交戦ごとに対にする。** 比較のアームは同じ周回で同じアリーナ種を受け取り、同じ場所・同じ予算・同じ戦力比・同じ編成を引く。差を交戦ごとに取れば、成績の散らばりの大部分を占める「どう引かれたか」が消え、区間はおよそ半分になる。**アリーナの比較では、対にすることが最も安い分散削減である。**

**[08-learning.md](08-learning.md) が交戦について並べている必要数の表は、この表より緩い基準の値である。** あちらは「平均の 2 標準誤差の区間が 0 を含まなくなる大きさ」、すなわち `(2 * sigma / delta)^2` であり、上の `7.85 * 2 * sigma^2 / delta^2` の 3.9 分の 1 になる。二つは別のことを言っている。**2 標準誤差は、その実行の平均が 0 でないと言えるかどうかの下限**であって、**二つの実行の差を主張できる大きさではない。** 決闘が報告する必要数は厳しい方であり、緩い方を下回っている測定は何も言っていないと読む。

### 最良として選ばれた差は、選択に使っていない実行で測り直す

上の必要数の式は、**一つの差を一度測ったとき**に何本要るかを言う。いくつかの設定を回して最も良かったものを取り出したときには、何も言わない。三つ回して最良を取れば、その最良は選択の分だけ上に振れた推定であり、式はその分を知らない。

**これは机上の注意ではない。** 戦術層の学習では、いくつかの設定のうち区間が 0 を含まずに最も良く見えたものが、選択に使っていない乱数種で回し直すと 0 と区別が付かなくなることが、繰り返し起きている([08-learning.md](08-learning.md))。同じ種で同時に取った基準線がアリーナ自身の偏りを示していて、基準線を引かなければ、その偏りを方策の手柄として報告していたこともある。決闘は既定で基準線のアームを同時に回すようにしてある([08-learning.md](08-learning.md) の [手順](08-learning.md#手順))。

したがって手順に一つ足す。**複数の候補から選んだものは、選択に使った測定とは別の実行で測り直し、その二度目だけを差として報告する。** 一度目は候補を並べるための測定であって、それ自体は主張ではない。乱数種を変えても試合は再現しない([../game/05-match-control.md](../game/05-match-control.md))ので、ここで種を変えることは「同じものをもう一度」を意味しない。**意味があるのは、選択に使った標本と確かめに使う標本が別であることだけである。**

**そのために、報告する数字にはそれを取った乱数種を併記する。** 種は再現のための情報ではなく、**その数字が候補選びに使った標本の上のものか、確かめの標本の上のものかを読者が判定するための情報である。** エピソード記録は種を含む設定一式を各行に持つ。

### エピソードあたりの費用

1 エピソードの実時間は、シミュレーション(ゲーム内の長さを実効の倍率で割ったもの)と、エピソードの切り替えの和である。

固定時計では実効の倍率は決まった値ではなく、CPU と、制御エージェントなら制御プロセスの答えの速さで決まる。盤面が大きくなるほど 1 ステップが重くなるので、試合の終盤ほど遅い([03-throughput.md](03-throughput.md))。切り替えは主にマップの読み込みで、計測エージェントも制御エージェントも、終了を見つけたフレームのうちに組み直しに入る。計測エージェントは終了と打ち切りをゲーム内 1 秒ごとに見る。

したがって毎時エピソード数は `並列数 * 3600 * 実効の倍率 / (ゲーム内の長さ + 切り替え * 実効の倍率)` で、打ち切り時間を短くするほど切り替えの割合が増える。**評価の予算は打ち切り時間と、その機材で実際に出る倍率で決まる。** `outcomes` は実行全体で終えたゲーム内時間を実時間で割った処理量を報告し、所要時間の見積もりをそれで出す。

## 評価の手順

以上をまとめると次の形になる。

1. **相手を固定する。** 内蔵 AI の 1 段階か、凍結したスクリプト方策か、凍結した学習済み方策。相手が変われば数字は比較できない。
2. **設定を固定する。** マップ、開始クレジット、開始ユニット、収入倍率、霧、打ち切り時間。乱数種は固定しても試合を再現しないが、**どの種で取った数字かは報告に併記する。** 候補選びに使った種か、確かめに使った種かで、同じ数字の意味が変わるからである([最良として選ばれた差は、選択に使っていない実行で測り直す](#最良として選ばれた差は選択に使っていない実行で測り直す))。
3. **両方の方策を同じ条件で回す。** 片方だけを後から回すと、機材の状態の違いが差として現れる。
4. **採点の平均と標準偏差を出し、基準のアームとの差を区間と補正後の判定で読む。** 差が確立されなければ、標準偏差から決まる必要エピソード数を見て回し足す。
5. **乱入込みで回す。** 学習も評価もスクリプト乱入者を注入した状態で行う([06-script-policy.md](06-script-policy.md))。人間は最終確認だけに使う。
6. **複数の候補から選んだものは、選択に使っていない実行で測り直す。** 選択に使った測定は候補を並べるためのものであって、差の主張ではない。**測り直す種では基準線を同時に取り、方策の数字からそれを引いて報告する。**

### 両方の方策は交互に回す

手順 3 の「同じ条件で回す」は、**片方を全部回してからもう片方、ではなく、インスタンスの中で交互に回す**ことで満たす。順に回すと、二つの数字は方策の違いに加えて「その間に機材の状態が変わった分」だけ違う。交互なら、その差は両方に等しく乗る。

実装では、1 インスタンスが `方策の数 * エピソード数` 回のエピソードを回し、方策を順番に切り替える。

### 記録するもの

試合が再現しないため、**乱数種だけを記録しても不具合は再現できない**([../game/05-match-control.md](../game/05-match-control.md))。エピソードごとに次を残す。1 行 1 エピソードの JSON として、終了のたびに追記する。途中で止めた実行でも、そこまでが残る。

| 項目 | 用途 | 実装 |
| --- | --- | --- |
| 設定一式と相手の識別 | 比較可能性 | `settings` と `arm` |
| 採点とその内訳 | 主指標 | `standing` から再計算できる形で残す |
| 決着か打ち切りか、決着なら勝者と時刻 | 重みの調整 | `winner` `timeout` `seconds` |
| 試合の途中の盤面 | 重みの調整 | `history`。一定のゲーム内時間ごとの、対戦者だけの最終状況 |
| 各層の決定回数と、契約の達成率 | どの層が効いたかの切り分け | `statistics` |
| 乱入者の有無と、乱入者が起こした事象 | 比較可能性と、除外すべき部隊の特定 | `interference`。乱入者の数、事象の列、触れられた部隊の一覧。乱入者がいなければ空 |
| ゲームのプロセスの中での試合の順番と、実際に読み込んだ地図 | インスタンスの最初の試合とそれ以降、地図ごとの切り分け | `order` と `map`。`order` はゲーム自身が数えた、それより前に同じプロセスで行った試合の数で、インスタンスの最初の試合が 0、ゲームが起動し直されるとまた 0 になる。`map` はエンジンが読み込んだ地図のファイル名 |
| 決定の遅延 | 答えが観測の 1 周期後に効いていたかの確認 | `latency`。`tactics`(全観測)と `operations`(領域ブロックを載せた観測。内政も同じ観測で決める)のそれぞれに、適用された答えの数 `answers`、適用されなかった答えの数 `missed`、遅延の `mean_ms` `p95_ms` `max_ms` と、それを戦術周期で割った `mean_periods` `p95_periods` `max_periods`([05-interface.md](05-interface.md) の 1 周期の遅れを固定する)。評価の報告はアームごとに、エピソードの戦術の 95 パーセンタイルの最大と、適用されなかった答えの合計を出す |

**記録は実行ごとに別のファイルになる。** 既定の書き出し先は `local/episodes/<実行の名前>-<日時>.jsonl` であり、設定の違う実行が一つのファイルに混ざらない。内蔵 AI 同士の測定(`outcomes`)はエピソード記録ではなくゲームプロセスの出力に `result:` の行として残り、それも実行ごとの `local/logs/outcomes/<日時>/` に残るので、後から数え直せる。

**乱入の欄は実行の出来を測る数字ではない。** 事象の列は乱入者自身(`rwintel/control/intruder.py` の `Log`)が集め、エピソードの終わりに `interference` として記録へ移り、他の項目と同じ 1 行の JSON に入る。乱入者が付いていれば、何もしなかったエピソードでも `intruders` が載る。乱入込みの数字と乱入なしの数字は別の量であり、記録からその区別が付かなければならないからである。エピソードの終わりには方策とその外側の指揮者が片付けられるので、記録はそれより先に乱入者の記録を読む。触れられた部隊の一覧を残すのは、後の学習実行がどの部隊の戦果を信号から落とすかを決めるためである([06-script-policy.md](06-script-policy.md))。乱入者が触れるのは指揮系統が制御している部隊だけなので、部隊がまだ編成されていない短いエピソードでは事象の列と部隊の一覧が空になる。人間の介入はこの欄には入らない。介入は起きたその瞬間に、そのとき見ていた盤面と対にして別の記録先へ書く必要があり([04-model-design.md](04-model-design.md))、エピソードの終わりの要約では盤面が失われるためである。

**採点の値そのものではなく素材を残す。** 重みは後から決まるものなので、素材を残しておけば過去の実行を新しい重みで採点し直せる。値だけを残すと、重みを変えるたびに回し直すことになる。

## 道具

方策の比較は `python -m rwintel.eval` である。ゲームと一緒に `python -m rwintel.runtime run` で起動するのは通常の実行と同じである([02-runtime.md](02-runtime.md))。

```bash
python -m rwintel.runtime run --count 4 -- eval --episodes 3 --arm script --arm arm --map Lake --max-seconds 300
```

`--arm` が比較する方策である。`script` が階梯に任せたもの、姿勢の名前(`expand` `tech` `arm` `defend` `decide`)を渡すとその姿勢に固定したものになる。`script:<名前>=<値>[,...]` はスクリプトの規則の一部を切り替えたもの、`script:baseline` はそれらの規則を全部外したものであり、規則ごとのアブレーションに使う(切り替えの一覧は [06-script-policy.md](06-script-policy.md) の規則の切り替え)。`baseline,frontier=on` のように左から順に効くので、規則を 1 つだけ足した方策も書ける。固定は人間が戦略層を引き取るための経路そのものであり([04-model-design.md](04-model-design.md))、比較のために作った仕掛けではない。`--episodes` は**方策ごと**の回数なので、上の例は 1 インスタンスあたり 6 エピソード、合計 24 になる。`--intrude` で乱入者を入れる。

作戦層を差し替えるアームもある。いずれも作戦層以外の五層はスクリプトのままである。

| アーム | 作戦層 |
| --- | --- |
| `operations:<path>` | `<path>` に保存した学習済みの網。運用時と同じく分布から抽選する。アーム名はファイル名から `operations-<名前>` になる |
| `operations-greedy:<path>` | 同じ網で、確率最大の答えを取る |
| `ops-home` | 全部隊を本拠地に最も近い領域へ送る |
| `ops-nearest` | 全部隊を、敵の戦力か敵の採掘施設がある領域のうち最も近いものへ送る |
| `ops-weakest` | 全部隊を、敵のいる領域のうち、自軍全体に対する敵の戦力が最も小さいものへ送る |
| `ops-richest` | 全部隊を、敵の採掘施設が最も多い領域へ送る |
| `ops-spawn` | 全部隊を、敵の出撃地点の領域へ送る |
| `ops-random` | 盤面にある領域から一様に抽選する |
| `ops-carry` | `ops-nearest` と同じ領域を選び、その領域で開いている移送の手段 (輸送の枠) の計画のうち最初のものを取る。移送の計画が開いていなければ、他の規則と同じく最初に開いている計画 (歩き) を取る |
| `ops-script` | スクリプトの規則を、学習した作戦層と同じ仕組みを通して動かす。決定は `script` と同じで、記録に作戦層の決定回数と戦略層の要求の達成度が載る |

`ops-home` から `ops-carry` までの七つはアブレーションである。作戦の決定を規則一行に置き換えたとき試合の採点がどれだけ動くか、すなわち作戦層が取り合っている幅を測るためにある。学習した作戦層が見直しの契機でだけ決めるのと同じく、これらも同じ契機でだけ決める。

```bash
python -m rwintel.runtime run --count 13 -- eval --episodes 4 --arm script --arm ops-random --arm operations:local/models/ops-rl.pt --intrude --difficulty -1 --max-seconds 900
```

内政層を差し替えるアームもある。いずれも内政層以外の五層はスクリプトのままである。

| アーム | 内政層 |
| --- | --- |
| `economy:<path>` | `<path>` に保存した学習済みの網。運用時と同じく分布から抽選する。アーム名はファイル名から `economy-<名前>` になる |
| `economy-greedy:<path>` | 同じ網で、確率最大の答えを取る |
| `eco-script` | スクリプトの判断器を、学習した内政層と同じ仕組みを通して動かす。決定は `script` と同じで、記録に内政層の決定の数が載る |

```bash
python -m rwintel.runtime run --count 12 -- eval --episodes 4 --arm script --arm economy:local/models/eco-rl.pt --difficulty 0 --max-seconds 900
```

### 相手の難易度

**作戦層の比較は、スクリプト六層の採点が上限にも下限にも張り付かない相手で行う。** 採点が -1 や +1 に張り付いた比較は、作戦層が良くなっても動かない。スクリプト六層は、難易度 0 の内蔵 AI には採点で下回り、難易度 -1 には上回る。**どちらの相手でも採点は上限にも下限にも張り付かず、両向きに散らばる。** 作戦層の比較の既定の相手は難易度 -1 とする。内政層の規則や学習した内政層を比べるときは難易度 0 を使う。難易度 0 は内蔵 AI の収入の倍率が 1.0 で、こちらと同じ足場で経済を比べられる唯一の相手である([../game/08-builtin-ai.md](../game/08-builtin-ai.md))。

報告は、アームごとに採点の平均と散らばり、四つの項それぞれの平均、決着した試合の勝ちと負けの数、そしてその数字を取った乱数種を出す。スクリプトの階梯を回したアームは、内政層の帳簿(手元のクレジットの平均、注文を出されなかった工場と仕事の無い建設機の割合、最初の工場・2 基目の採掘施設・2 基目の工場が立った時刻)と、姿勢ごとの滞在時間と姿勢の変わった回数も出す。工場の生産キューは観測に載っていないので、注文を出されなかった工場が止まっているとは限らない。この割合が言うのは、内政層が生産を控えた頻度(予約を差し引いたクレジット不足、ユニット上限、軍備の配分比)である。

**帳簿はクレジットの行き先と失い方も出す。** 行き先は、注文で約束したクレジットを使い道ごと(役割ごとの軍備、建設機、採掘施設、工場、砲台、強化)に割った割合である。注文は仕事が始まってから引き落とされるので、始まらなかった注文も数える。これに、最初の工場が立ってから完成した工場が 1 基も無かった期間の割合と、手元のクレジットが工場を足す閾値を超えていた期間の割合を並べる。失い方は、失った自軍の価値を、役割ごと、部隊に属していたか未配属か、敵の武装した建物の射程(と少しの余裕)の内で失ったか、に割った割合である(`rwintel/control/policy/audit.py`)。収入で勝っていて軍事価値で負けている方策は、どこかでユニットを失っている。この三つの切り方が、作るものの誤り、単独で向かった増援、固定防御への突入を分ける。

各アームについて、採点の標準偏差と、そこから決まる差 0.05、0.10、0.20 それぞれの必要エピソード数を出す。これは次の実行の予算を決めるための数である。エピソードごとの採点とその内訳は `--verbose` のときに出る。

**比較は、各アームを基準のアームと並べて行う。** 基準は `--reference` で指定し、無ければ最初の `--arm` である。`--from` の報告で `--arm` も無ければ、条件ごとに記録に最初に現れたアームを基準にする。`--from` に `--arm` を添えると、実行したときと同じ基準で読める。各比較について、平均の差、その 95 パーセント区間(両側の標準誤差を別々に取る Welch の形)、正規近似による両側の p 値を出す。そのうえで、**報告に並んだすべての比較をまとめて Holm の方法で補正し**、補正後も有意なものだけを「差がある」と書く。十数のアームを一度に比べると、5 パーセントの水準でも偶然に有意な比較が一つ二つ出る。補正は、並んだ比較のどれか一つでも誤りである確率を 5 パーセントに抑える。

**設定の違うエピソードは合わせず、比べもしない。** エピソードは、乱数種を除いた設定一式と乱入者の有無で分けて報告する。分けたときは、違う項目だけを見出しに添える。乱数種だけが違うエピソードは同じ測定の繰り返しであり、合わせて報告する。確かめのために乱数種を変えて回した実行は、まとめて読める。**`--map` を繰り返すと、地図を順に回す。** 1 つの地図でアームを一巡してから次の地図へ移るので、どのアームも同じ地図を同じ順で戦う。報告は地図ごとに分けたうえで、地図だけが違う条件を合わせた節(`maps pooled`)も出し、その比較も補正の対象に入れる。複数のプロセスで共有した試合のうち、途中で同期が崩れたものは報告から除き、その件数を出す。

**比較の後に、アーム、地図、インスタンスの中での順番ごとの平均の得点を並べる。** 順番は、インスタンスの最初の試合(`first`)とそれ以降(`later`)の二つに分け、`order` を持たない古い記録は `unknown` とする。実行の報告でも `--from` の報告でも同じものを出す。最初の試合だけ条件が違っていないかを、地図ごとに確かめるためである。

報告の最後は、決着した試合を盤面から予測できるかである。まず、使っている重みで、決着した試合の終局前の盤面を採点し、勝者を当てた割合を出す。そのうえで、その場で合わせた重みを、終局までの時間ごとに出す([重みの決め方](#重みの決め方))。`history` を持たない古い記録からは合わせられず、報告はそのことを書く。

実行のたびに全エピソードが JSON 行として残るので、後から重みを変えて採点し直せる。書き出し先は実行の最初のログ行に出る。

```bash
python -m rwintel.eval --from local/episodes/script-arm-20260101-120000.jsonl
python -m rwintel.eval --from run-a.jsonl --fit-out local/weights-a.json
python -m rwintel.eval --from run-b.jsonl --weights local/weights-a.json
```

| オプション | 意味 |
| --- | --- |
| `--from <記録>...` | 実行せず、記録を読んで報告する。複数を受け取り、同じアームと同じ条件のものを合わせる |
| `--reference <アーム>` | 比較の基準にするアーム。無ければ最初の `--arm` |
| `--weights default\|opening\|<パス>` | 打ち切りの採点に使う重み。`default` は採用した重み、`opening` は軍事価値差だけ |
| `--lead <秒>` | 重みを合わせる盤面を終局の何秒前に取るか。既定は 60 |
| `--fit-out <パス>` | `--lead` で合わせた重みをこのファイルに書く |
| `--verbose` | エピソードごとの採点も出す |

### 初期値の探索

スクリプトの規則の初期値のうち探索の対象にしたもの([06-script-policy.md](06-script-policy.md) の規則の切り替え)は、`python -m rwintel.eval.search` で探す。

```bash
python -m rwintel.eval.search --count 13 --candidates 16 --rounds 3 --episodes 3 --map Lake --map Beach --map Big --difficulty 0 --intrude
python -m rwintel.eval.search --count 13 --confirm tune.attack_edge=0.1,tune.push_odds=1.1 --confirm-episodes 12 --map Lake --map Beach --map Big
```

候補は、今の値そのものと、各値の範囲から層別に抽選した設定(ラテン超方格)である。層別にするのは、候補が少なくても各値の範囲のどの部分も誰かが覆うようにするためである。候補は successive halving で絞る。各段は生き残った候補を同じ実行のアームとして交互に回し、平均採点の上位半分を残し、次の段のエピソードを倍にする。今の値は、順位によらずすべての段に残す。すべてをそれと比べるからである。

**勝ち残った設定は、選ぶのに使ったエピソードの上では上に振れている**([最良として選ばれた差は、選択に使っていない実行で測り直す](#最良として選ばれた差は選択に使っていない実行で測り直す))。そこで、どの段も使っていない乱数種(探索の種の 1000 先)で今の値と並べて測り直し、その差だけを報告する。各段は `python -m rwintel.runtime run ... -- eval ...` の実行であり、記録は段ごとに別の journal に残る。探索の結果は `local/reports/search-<日時>.json` に書く。採用するときは、確かめた値を `tuning.py` の既定値に書き戻す。部隊の数や工場の数のように数と比べる値は、同じ振る舞いになる整数にして書き戻す。`tuning.py` の既定値は、この手順で選んで確かめた値である。

内蔵 AI 同士を戦わせて分布だけを見るには `outcomes` を使う。ローカルプレイヤーを含む余分なプレイヤーを観戦者に移し、残した 2 名を戦わせる。既存のプレイヤーを AI に差し替えることはできない([../game/05-match-control.md](../game/05-match-control.md))。`--levels 3,-2` で対戦者ごとの難易度を書き分ける。

```bash
python -m rwintel.runtime outcomes --count 8 --episodes 6 --map Islands --difficulty 1
```

勝率とその標準誤差、長さの分布、価値差の平均と散らばり、そして勝率と価値差のそれぞれで差を検出するのに要るエピソード数と、その並列数での所要時間を報告する。報告は `local/logs/outcomes/<日時>/summary.txt` にも残る。
